# IoT Benchmark 上手教程：第二篇文章设计

## 目标

续写 CSDN《基准测试工具之你不知道的两三事》系列的第二篇，面向首次使用时序数据库基准测试工具的读者，完成一次可复现的 IoT Benchmark 入门操作。文章以 IoTDB 2.x 的默认写入测试为主线，不输出未经实际执行所得的性能结论。

## 读者与边界

- 读者已经了解数据库基准测试的基本用途，但尚未实际运行过工具。
- 读者具备基本命令行和 Java 项目构建经验。
- 本文聚焦 IoT Benchmark 的最小闭环：准备、构建、运行、配置、读报告与控制变量。
- 本文不进行多数据库横向排名，不给出任何脱离硬件和配置上下文的性能数字。

## 文章方案

标题暂定为《IoT Benchmark 上手：从一次时序数据库写入测试开始》。正文保持首篇的科普式中文写法，先解释为什么要这样做，再给出命令和参数；每节只引入完成当前步骤所需的信息。

文章依次包含：

1. 前沿：承接首篇，说明一次可用测试由工作负载、环境和结果共同构成。
2. 准备工作：列出 Java 17、Maven、目标 IoTDB 2.x 服务以及版本匹配要求。
3. 第一次测试：从克隆、构建到进入 IoTDB 2.0 成品目录并运行默认写入测试。
4. 三个关键配置：`DB_SWITCH`、数据规模与并发、`OPERATION_PROPORTION` 的负载比例。
5. 结果解读：解释总耗时、成功与失败操作数、吞吐量和 P99 延迟，强调它们必须结合配置阅读。
6. 常见误区：固定环境、一次只改一个变量、重复执行，并保存完整配置与日志。
7. 小结：给出测试前检查清单，为下一篇“更贴近业务的负载设计”衔接。

## 事实与来源

技术事实以 [thulab/iot-benchmark](https://github.com/thulab/iot-benchmark) 当前 `README-cn.md` 为准：项目要求 Java 17 和 Maven；IoTDB 2.x 示例使用 6667 端口；常规、数据生成、正确性写入、正确性查询四种工作模式由 `BENCHMARK_WORK_MODE` 选择；日志目录保存运行信息。首篇的叙述节奏与主题边界参考用户提供的 CSDN 原文。

## 验收标准

- 可由读者依次执行命令完成默认写入测试。
- 代码块中的路径和配置项与当前项目 README 一致。
- 不将示例输出中的吞吐量误写成普遍结论。
- 清楚说明公平比较所需的环境与变量控制。
- 成稿使用 YAML frontmatter，存入 `SpriCoder-Astro/content/posts/` 的对应主题目录；未发布内容放入 `SpriCoder-Astro/content/drafts/`。
